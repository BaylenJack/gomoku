# hint.js v3 — 威胁空间搜索引擎设计

日期: 2026-08-08
背景: 用户反馈 v2 提示引擎棋力不足,连输给对手。v2 是"两层前瞻 + 启发式打分",
把活三/跳三/冲四/活四压成同一档分数(16000),无法识别强制连杀手段。

## 核心思路: 威胁阶梯 + 强制搜索

五子棋的胜负由"强制棋序"决定: 活四 → 冲四 → 活三 → 双威胁。
引擎不再只打分数,而是:

1. **精确棋形分类**: 每个候选落点按 4 个方向分类为 活四/冲四/活三/跳三/跳二/眠形。
2. **VCF 搜索** (连续冲四连杀): 己方有冲四时,对方只能堵端点(唯一/至多两个选择),
   搜索可全深度展开,直到发现"对方怎么堵都是死"。这是连杀,也是棋力飞跃的关键。
3. **VCT 搜索** (活三/双威胁推进): 无冲四链可杀时,用活三+双威胁制造"挡不住"的强制
   胜势,深度 2-4(链上出现冲四则加深为 VCF)。
4. **防守优先级**: 对手活四 → 必堵; 对手活三/双威胁 → 优先消除。
5. **启发式保底**: 威胁搜索预算(节点/时间)内找不到强制手段 → 退回改进的 v2 打分
   (细分跳三/活三、对称去重、候选池优化)。

## 棋形分类器

对 `(x,y)` 落 `color`,沿 4 方向各自计算:
- `n` 连续段长, `open` 两端空位数
- 精确类型: FIVE / OPEN_FOUR(两端都开) / CLOSED_FOUR(冲四,一端封) /
  OPEN_THREE(活三) / JUMP_THREE(跳三 XX_X / X_XX) / SLEEP_THREE(眠三) /
  OPEN_TWO / JUMP_TWO / 其他

## 搜索结构

```
computeBest(board, color):
  1. 我方有直接成五点 → 返回
  2. 对手下一手成五 → 必堵(选最佳堵点)
  3. VCF(我方, 深度不限, 节点预算 20 万): 找到连杀 → 返回第一手
  4. VCF(对手视角, 同预算): 对手有连杀 → 必须堵/消其关键冲四
  5. VCT(我方, 深度 2-4, 预算共享): 找到强制胜势 → 返回
  6. VCT(对手视角): 对手有强制胜势 → 防守(消除威胁)
  7. 启发式保底(改进 v2 打分)
```

### VCF 细节
- 当前玩家若有冲四点集: 尝试每个冲四点落子, 对方所有合法堵点(每个冲四的开放端点,
  若两端开放则有 2 个)逐一应对。
- 己方落子后若成五 → 赢; 若我方制造出新的冲四 → 继续强制对方。
- 防守方若同时存在自己的活四/冲四, 允许"先杀对方"的一手(互杀处理)。
- 节点预算内暴力展开, 剪枝: 无冲四可下且无成五点即停(该分支失败)。

### VCT 细节
- 在无冲四可下的局面, 尝试"活三点 + 双威胁点": 落子后形成 >=2 个
  活三/冲四级威胁(双活三、活三+冲四) → 对方必须同时堵, 堵不完 → 胜势。
- 深度限制 2-4(己方落 → 对方挡 → 己方再落), 链中若出现冲四则转 VCF 逻辑。

### 互杀处理
VCF/VCT 双方轮流, 各自都尝试"我先成五/我先冲四", 用极小极大框架。
不引入正式 alpha-beta(深度浅 + 强制性强, 开销不值得), 但会做"唯一的强制应对"
提前终止(强制走法唯一时直接走, 不分支)。

## 性能预算

- 单次 computeBest 总预算: 节点 20 万 / 时间 600ms, 先到先停。
- 保底打分路径本身 <50ms(与 v2 相当)。
- 手机上 20 万节点纯 JS 大约 200-400ms, 在预算内。

## 接口与集成

- 保持 `computeBest(board, color)` 不变, 返回 `{x, y}`。
- 保持 UMD 包装, 前端 `loadHintEngine()` 动态加载方式不变。
- hint.js 版本号已在 app.js 固定为 `v=3`, 引擎内部结构变化不影响加载。

## 测试计划 (hint.test.js)

新增战术测试(全部可由现有 vm 沙箱运行):
1. 单冲四(唯一堵)后连续冲四 → 最终成五 (VCF 连杀 3-5 手)
2. 双活三制造 → 对手挡不住 (VCT 双威胁)
3. 对手双活三/双威胁局面 → 优先防守消除
4. 跳三缺口点识别 (已有 v2 测试保留)
5. 跳四冲四识别 (跳四也是强制手)
6. 性能: 复杂局面含威胁搜索 < 200ms (在现有性能测试基础上强化局面)
7. 既有 9 个 v2 测试全部保留, 保证不回归

## 非目标

- 不做正式 alpha-beta/完整 MiniMax(在浏览器 600ms 预算下复杂度不可控)
- 不做蒙特卡洛树搜索
- 不改服务端/前端集成, 只改 hint.js + 测试
